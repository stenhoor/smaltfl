# ADR 0021: Time: a month to pick a day from, the day itself, and every version of it

- **Status:** accepted, 2026-11-13. The maintainer answered Q-181 to Q-192 in a session, after research into the code
  and into how other tools handle time (docs/OPEN_QUESTIONS.md). It is built in the slices of §9.
- **Date:** 2026-11-13
- **Builds on:**
  - [ADR 0006](0006-integrity.md): integrity and the record.
  - [ADR 0008 §10](0008-visual-first-news.md): a day shows only that day.
  - [ADR 0009](0009-paused-not-published.md): paused, not published. Amendment 1 covers fills and a day's versions.
  - [ADR 0015](0015-the-bronze-layer.md): the ontology people edit.
  - [ADR 0018](0018-phone-tablet-and-desktop.md): phone, tablet and desktop.
  - [ADR 0020](0020-the-estate-as-a-company.md): Larkspur.
- **Changes:** Q-62. A corrected file that passes no longer replaces a fill on its own; every correction waits for a
  decision (Q-183).

## Context

**The request.** The maintainer finds moving through the days odd. Today one screen has a strip of days with the flow
under it. They would rather start high up, picking a day, then drill into that day and see its flow: two separate
screens. That ties into a larger question, how the flows handle time.
- The ontology must change over time and be hashed to the day a run used it. If something about the business changed on
  a given day, you can see what it was that day, and so why the data ran the way it did.
- Going back in time should show what happened:
  - what data was provided, and what we went with;
  - whether history was corrected after a new file arrived a few days later;
  - the branches between them.

The owner said the same on 2026-11-08 (Q-49): "We should always be able to get back to what was true, what was used
later if anything, and we should be able to update what was used if we get better info later."

**What the app does today:**
- **Choosing a day runs it.**
  - Picking a day on the strip runs it in the browser (`useLoad` → `runLoad` → `run`), and every view follows the day on
    screen (`shownRun`).
  - It runs under today's document, so a past day re-runs under any ontology edits made since. No path runs a past day
    under the document it first ran with, although every run's document and plan are kept in the record by hash.
  - The engine lives in memory. A day judged after a gap reads "Not judged yet", because the history it is judged
    against grows only from the days this browser ran.
- **The record is a sound base** (log/1, IndexedDB, RFC 9162). For each run it keeps:
  - the files' sha256s, the manifest, the plan, the flow hash, measures and claims;
  - decisions, releases, withdrawals, flow changes and file checks, each with who, when and why.

  It is shown only in the Runs view, as an audit list of this browser's runs.
- **The ontology has no time.** A manifest names the flow, policies and ontology hashes (run/1). An edit applies from
  the next run (ADR 0015 §4), with no effective date. Rule switches and gate modes live in notebook cells, outside the
  ontology hash.
- **Corrections are half built:**
  - Fills are built: derived runs, donors, and `filled_from` on every row.
  - Replace the file is kept in memory only (Q-155).
  - A republished file is noticed, but nothing re-runs its day.
  - The data list holds one file a day for each source, so a later file for the same day has nowhere to go (Q-77).
  - `dayVersions` (fill.ts) lists a day's versions, but only fills reach its sheet.

**What other tools do** (sources at the end):
- *Overview first, details on demand* (Shneiderman).
- **Orchestrators:**
  - Airflow puts runs against tasks in a grid, and has a calendar.
  - Dagster gives each asset a status bar of its partitions.
  - GitHub Actions makes a re-run a numbered attempt, the latest shown and the earlier ones a tap away.
  - dbt Cloud bannered a resumed run with how it differs.
  - Bug reports from Dagster users say a partition's status must follow its latest run.
- **Observability tools:**
  - Bigeye gives each check a scorecard of daily bars.
  - Monte Carlo, Datadog and PagerDuty tell an incident as a timeline of typed, linkable entries, with a condensed form.
- **Version histories** (Google Docs, Figma, Notion) list the versions, render one as it was, and highlight what
  changed.
- **Two kinds of time.** Data that changes keeps two clocks:
  - *valid time*: when a fact holds;
  - *record time*: when it was known.

  Fowler calls them actual and record history. SQL:2011 and XTDB build them in. ALFRED keeps every vintage of a series,
  "as it appeared at various points in history".
- **What was published** is a pointer that only a decision moves (Iceberg's write-audit-publish, lakeFS's gated
  commits).
- **Diffs.** Dolt opens a diff on a summary, then shows rows and cells.
- **Ontology and schema changes:**
  - Foundry reviews ontology changes as proposals with a changelog.
  - DataHub and OpenMetadata keep schema versions with diffs.
  - Each dates a change only by when it was made. An ontology also needs the business day it takes effect.

## Decision

### 1. Two kinds of time, and what we went with

- **The day** (valid time). The business day a file covers, and the day from which an ontology version is in force.
- **When it was known** (record time). When a file arrived, a run ran, a decision was taken or an ontology version was
  recorded. It is only ever appended to. In the demo, the story's clock sets it (§6).
- **What we went with.** For each day and output, the version readers get.
  - It moves only by a passing run on the day's first files, as today, or by a decision.
  - Every earlier version stays reachable, never overwritten.
- **The record is the event log.** Every fact above is an entry, so any view "as known on" a moment reads the entries
  recorded by then.

A run is a point: a day, as known at a moment. Three hashes name it: the day's files (sha256), the rules in force that
day as known then (§5), and the plan, which follows from both.

### 2. Every version of a day

- **Kinds of version:**
  - *as arrived*: the day's first files;
  - *filled*: from another day's file (ADR 0009 amendment 1);
  - *corrected*: a file re-sent, or arriving late, for the day;
  - *restated*: under a back-dated ontology change (§5);
  - *what-if*: any files under any rules (§4). It never enters the record unless someone decides to make it a version.
- **A version is like a commit.** Each is a run with its own manifest, kept with when it was made, which files and
  which rules it used, what was decided, by whom and why. A day can be corrected any number of times. The record
  always says what showed up and what was used.
- **Every correction waits for a decision** (Q-183), even when its run passes. Only the day's first files publish on
  their own when they pass, as today. This supersedes Q-62.
- **A later file for the same day is a version of that day** (Q-77, for a day's file). The data list gains deliveries:
  each file for a day, with the time it arrived.

- **Two named dates at the top** (Q-188), from the start:
  - **For the day** moves between months.
  - **As known on** defaults to now and shows the month as it stood at a past moment.
- **The trend band** (Q-186). Where the data list names a posture product, a one-line band above the calendar gives the
  product's score on each day published, so a dip lines up with its day. The full dashboard stays its own screen, for
  the day picked.
- **The calendar** (Q-182) has seven columns.
  - Each day shows its date and what became of it, as a glyph and never by colour alone or an average: published,
    paused, published as is, unusual, filled, corrected (with its count of versions), not judged, not arrived.
  - A tap or hover shows its headline, the files received, the decision and its versions, and **Open the day ›**.
- **The grid**, from tablet width, puts files and steps against days.
  - Its rows are the notebooks, each opening to its files and steps.
  - A cell is that file's or step's state on the day, so a reader sees which file broke on which day.
  - Filters: waiting for a decision, corrected, held.
- **On a phone:** the calendar on top and the chosen day's summary below.
- **It reads the record**, so drawing it runs nothing.

### 4. The day screen

- **Its own URL** (`#/day/2024-03-12`, a version `#/day/2024-03-12/v3`, and the as-known-on moment when one is set).
  Back returns to the month (*‹ March*).
- **Its header:**
  - the day and its outcome;
  - the neighbouring days, as a week strip on wide screens;
  - the rules in force: the version, its hash, and what changed since the day before;
  - the day's lifecycle: arrived → checked → held → decided → published, then any corrections.
- **The versions**, listed like commits, with what was used marked. Any version can be opened.
- **The flow:** the canvas and the sheets as today.
  - Opening a day, or any version, runs the whole flow in the browser on that version's inputs: its files by hash and
    its rules in force. It is judged against the recorded days before it. The page then compares its run with the
    recorded manifest and says plainly if they differ.
  - So opening the original, a correction or a what-if shows what would have happened (Q-187).
- **The day's story:** a timeline of typed entries in time order, with a condensed form.
  - A file arrived (its hash), the run, held because…, decided by… because…, published, a correction arrived…
  - Each entry is linkable.
- **Compare two versions** (Q-187):
  - first a summary: files, rules, decision, and for each output its rows and whether its content changed;
  - then, for any output, its row and cell diffs: rows added and removed, cells changed. Rows are matched by the
    output's key (a gold contract's or gate's), or by row hash where there is no key.
- **What-if** (Q-191). Pick any file version for each source and any rules version, and the whole flow runs. The result
  is marked as a what-if, kept apart from the record, and never published unless someone makes it a decided version.

### 5. The ontology over time

- **Effective-dated** (Q-184). The flow keeps a base and dated change sets. Each change set has:
  - `from`: the business day it takes effect;
  - `recorded`: when it was made;
  - who made it and why, and its edits: the app's edits as they are recorded today.

  The rules in force on a day, as known at a moment, are the base plus every change set from that day or before,
  recorded by then.
- **One hash for the rules in force.** It covers the ontology and the notebook-cell switches edits change today (rule
  switches, gate modes), under a new tag with test vectors (CLAUDE.md: a new encoding goes in an ADR first). Every run's
  manifest names it.
- **By default a change takes effect from the next day to arrive** (Q-189), so no past day moves. Back-dating is a
  choice on the edit form: *in force from* a date, after the form says how many past days it would touch.
- **A back-dated change restates past days** (Q-190).
  - Each day it touches gets a restated version, run in the background.
  - The month marks the days whose outcome would change.
  - One decision restates them, with a reason, and any day can be unticked. Days whose outcome doesn't change are
    noted, not decided again.
- **The Ontology screen** follows the day and the as-known-on moment. It lists the versions, and any two can be
  compared.
- **Changes that arrive as data stay data**, such as Larkspur's reorg in the HR extract. Ontology versions are for the
  rules people set.
- **Back-dating comes with effective dating, in one slice** (Q-197). Every recorded day of the demos is past, so an
  edit from the next day alone would change nothing on screen: the edit form offers the day on screen or any date, and
  says how many published days that touches.

### 6. The recorded month

- **March is recorded history** (Q-181).
  - The build runs each generated flow's month in order and records it: every run, as the build's entries in the
    record, at the story's times.
  - The record ships as a file listed in loads.json, and the browser imports it on open.
  - What the visitor does is appended on top, kept in their browser, with *back to the record as shipped*.
  - Only days still waiting for a decision are the visitor's to decide.
- **Judging needs no prior runs in this browser.** A day's history comes from the recorded days before it, as known
  then, so a day picked out of order is judged as it was.
- **Larkspur's story** (Q-192) is written in `examples/larkspur/story.json` and confirmed in slice 2. It holds:
  - who decided what, when and why;
  - each delivery's arrival time, the late and corrected files written by the generator;
  - the ontology changes.

  It includes a corrected file, a day corrected twice, a late file, and ontology changes forward and back-dated. Proposed:
  - Mon 4, the MFA file empty: kept back, since Larkspur's flow has no fill step (Q-194). The real file arrives late, on
    Tue 5, and is decided and published.
  - Wed 6, the backup file stale: kept back. The real file arrives Thu 7 and is published as a correction.
  - Thu 7, the logging file refused: re-sent the same day, decided.
  - Tue 12, the WAF band: published as is, with the reason.
  - Mon 18, the HR extract: re-sent with the teams under their new department, right, and published (Q-195).
  - Thu 21, the TLS file doubled: re-sent with half its repeats removed, still wrong, kept back; then sent again fully
    deduplicated, and published (Q-195). Three versions.
  - The ontology, forward: the WAF band tightened to 10% from Mon 18, recorded Fri 15. Back-dated: a rule recorded Mon
    25, in force from Fri 1, restating the days it touches under one decision.
  - Fri 8 and Tue 26 kept back, Wed 13 and Tue 19 published as is, each with the security lead's reason (Q-196).
  - Now is Mon Apr 1, 08:00. Sat 23 (the DR exercises) and Thu 28 (the loop) still wait for the visitor.
- **The control estate and the sign-ins** record their months with no scripted decisions. Their paused days wait for
  the visitor, as their walks say.

### 7. As known on

From the first slice, *as known on* a moment shows:
- the month with only the days whose files had arrived by then;
- each day as it stood then.

Each later slice adds its facts to the same filter: decisions, corrections, restatements and ontology versions.

### 8. What it changes

- **The strip of days goes.** Days are picked on the month and stepped through on the day screen.
- **The views:**
  - Runs becomes the Record, the audit view.
  - Results (the posture dashboard) follows the day picked.
  - Ontology and Policies follow the day and the as-known-on moment.
- **tools/browser/tour.cjs reaches a day by its URL**, and every stop set moves to it in slice 1 (almost all pick days).
- **Two questions settle as their slices are built:**
  - Q-51 (an earlier passing day moving the names back): outputs keep their days, and what we went with is a pointer
    for each day.
  - Q-155 (Replace the file, recorded): it becomes a delivery, a corrected version, with its own entry.
- **The build records each month**, about two minutes more for Larkspur. Each corrected or late file adds a file to the
  data.

### 9. The slices

1. **Two screens and the recorded runs** (Q-185):
   - the build runs and records each generated month;
   - the browser imports the record;
   - the month screen: the calendar, the grid, the trend band, both dates;
   - the day screen: the flow, the lifecycle, the story of its recorded runs, a run compared with its record;
   - URLs, and tour.cjs and the stop sets moved to them.
2. **The recorded story:**
   - deliveries in the data list (late and corrected files, a day corrected twice) and the generator's corrected files;
   - Larkspur's `story.json` (decisions with who, when and why);
   - the day's versions on its screen, and corrections that wait for a decision.
3. **Flip and compare:**
   - any version opened runs the whole flow;
   - the compare summary;
   - row and cell diffs by key.
4. **The ontology over time:**
   - dated change sets, and the rules-in-force hash with test vectors;
   - *in force from* on every edit;
   - a back-dated change restating days under one decision;
   - the Ontology screen's versions, and the story's ontology changes.
5. **What-if runs.**

Each slice keeps every screen working at phone, tablet and desktop size (ADR 0018), with its stop sets.

## As built

**Slice 1, the two screens and the recorded runs (2026-11-13):**

- **The recorded month** (`src/core/month.ts`, `smaltfl-month/1`; `test/month.test.ts`):
  - the build's `run` entries, in the record's own shape, by `build`, at the story's times: a day's latest export time
    where its files say one, else 06:00 UTC;
  - each run's manifest by its hash, and the posture product's group score and coverage on each day it published;
  - `now`, the morning after the month's last day.

  The page numbers the build's entries below its own (`layered`). Whatever reads the record (a day's tails, skips,
  pauses and levels, what readers see) reads both, and this browser's record and its hash chain are unchanged.
- **The recorder** (`scripts/data/record.ts`, run by `node scripts/data/record.mjs`) runs each day of the generated
  month in order, as the page runs it:
  - its claims judged against the base history and the tails of the recorded days before it, with skips, accepted
    levels, kept samples and the file facts the fresh check reads;
  - the watched steps told in the engine, whose claims `RunResult.told` now returns beside the manifest (no hash
    includes it).

  The build runs it after the histories, inside the cache keyed by the data's hash. Recording a month again gives the
  same manifests, hash for hash; only the build commit each claim names differs.

- **The month screen** (`renderMonth`) is where a flow with days opens (`#month`):

  - *As known on* is now or the end of any day of the month. A past moment shows only the entries recorded by then:
    the later days not arrived yet, and the trend only up to that day.
  - The trend band reads the recorded posture.
  - The calendar marks each day by its latest run: published, paused, unusual, not judged, failed, what a decision made
    of it, not arrived. A day run here is said as the page says it (its pause and what holds it, else its story's
    verdict). Any other day is said by its recorded run (its holds, else its judged dataset's claim).
  - A tap gives the day's summary below the calendar, or beside it on a wide screen: its headline, when it arrived,
    its rows, what waits, whether the build recorded it and whether its run here matched. Then **Open the day ›**.
  - The grid, from 820 px, has a row for each notebook, with the files it reads first; ▸ opens it to each file and
    step. A cell is refused, held, unusual, not judged, fine or not built.
  - **Check every day here ▶** runs every day in the browser in order, the paused ones too, and counts the days checked
    against the record.
- **The day screen** (`#day/YYYY-MM-DD`; `renderLoads` draws its head), with the canvas below:
  - back to the month, and the days either side;
  - the day and its mark;
  - what happened to it: arrived, checked, held or published, decided;
  - the record's line;
  - the pause, with **Decide ›**;
  - the day's story: each run and decision of the day, the build's and this browser's, in order.
- **A day opened is run here and checked against its record** (`checkAgainst`): the same plan, the same content hash
  for every dataset stored, the same holds. A run here has its own ingest times and run id, so its manifest's hash isn't
  the record's, and the check compares what the two manifests say instead. A day run under the flow as edited here, or
  on other files, says so and isn't compared. Every day checked so far has matched:
  - Larkspur's Fri 1, Thu 7, Tue 12 and Mon 18;
  - the control estate's Wed 6, Thu 7, Fri 8, Tue 12, Thu 21 and Sat 23;
  - the sign-ins' Tue 12, Thu 14, Fri 15, Mon 18, Tue 19 and Wed 20.
- **Two clocks.** The build's entries carry the story's times, and this browser's entries its own clock.
  - A wait measured from a moment in the story runs to the record's `now` (`storyMs`): the sign-ins' Fri 15 has waited
    7 days, not since 2024.
  - A time in another year than its day says its year.
- **A day held is headed by what holds it**, whether it was run here or recorded (`calendarDay`, as `stateOfRun`
  heads it): Larkspur's Mon 18 by org_chain's broken rule, not the followed dataset's verdict. This partly answers
  ADR 0020 slice 7's open point: the month and the day's story now say why a refused file's day is paused (Thu 7:
  *logging_coverage: file has 5 of 6 columns*). The status line, the decision bar and the file's Quality tab still
  don't.
- **What the recorded days change for a held day:**
  - A fill may take any recorded day that published, including a later one: the sign-ins' Fri 15 is offered Sat 16 to
    carry back.
  - The fill's row draws the week before the day from the recorded days, not only the days run here.
- **The first load** (tools/browser/load.cjs, Larkspur at desktop size, the median of three): the month draws at
  0.8 s, once the recorded month is read (0.43 s of that). The first day runs behind it and is shown at 6.4 s, about as
  long as it took on the same machine before this slice.
- **The browser tools reach a day by its link.** `window.__smaltflMonth` says each day as the calendar does.
  tools/browser/tour.cjs finds a stop's `day` by it and opens `#day/…`, and a stop's `view` is its hash.
  `tools/browser/stops/month.json` walks the month. The stop sets on Larkspur, the control estate and the sign-ins pass
  at every size.

**Where the text changed as it was built:**
- The day's link is `#day/2024-03-12`, like the app's other views (`#flow`, `#ontology`), not `#/day/…`. A version's
  link, and an as-known-on moment in the link, wait for slice 2.
- *For the day* has no arrows between months: each demo records one month.
- The day's neighbours are two buttons, not a week strip. The month is a tap away.
- These wait for slice 2, which has corrections to show: the calendar's *corrected* mark, the files and versions in a
  day's summary, and the grid's filters. (Slice 2 built the first two; the grid's filters wait for slice 3.)
- The Record view (once Runs) still lists this browser's runs and record. The build's runs are told on the month and in
  each day's story.
- The recorder takes about five minutes for Larkspur, not two. It runs each day's twenty judges on one thread, where the
  page spreads them over workers. It is cached by the data's hash, so it reruns only when the data or the flow changes.

**Not yet:**
- Per-unit posture trends in Results still come from the days run here (**Check every day here ▶**).
- The month file is mostly the measures that judge a day out of order: 3.2 of Larkspur's 5.0 MB. Fetching them only
  when a day first runs here would cut what the month needs before it draws.
- The page reads the recorded month before it runs the first day, though the month's first day needs none of it: 0.43 s

- The taxi example's stop sets, tools/browser/episode.cjs and integrity.cjs are moved to the new screens but not run:

**Slice 2, first part: corrections wait for a decision (2026-11-13):**

- **Found first, fixed in its own PR (Q-193, ADR 0010 §16).** On Larkspur and the control estate, Publish as is was
  refused by the engine: they watch several datasets, so a release must cite one decision per held file. One choice for
  the day is now recorded as a decision for each held file and one release citing them all.
- **A run can correct an earlier run of its day** (`RunOptions.correction`: the run it corrects and the sources whose
  files were sent again). The runtime records it in the manifest as `correction`. The field is optional, so a run that
  corrects nothing hashes as before.
- **The correction hold.** `holdsOf` holds every output each re-sent file reaches, `by: 'correction'` ("a later file for
  its day: it waits for a decision"), whatever its checks say (Q-183). With several watched datasets the hold is about
  the re-sent file's load. Verify and the audit compute it again from the manifest, so they agree with no change of
  their own, and a decision's release publishes it. Only a day's first files publish on their own.
- **Replace the file is a later delivery of the day** (Q-155). The replaced file's run corrects the day's latest run
  here, and its record entry keeps what it corrects. It is offered only where the held file is the one it replaces.
- **The day screen says it.** The lifecycle reads Held, then *Sent again: auth*, then the decision. A line says the
  later file waits for a decision, as every correction does, and the day's story names the files sent again.
- **Checked:**
  - `test/correction.test.ts`: a corrected file passes its checks and still waits, publishes nothing, names the run it
    corrects, verifies, and is published by a decision.
  - `tools/browser/stops/fixes.json`: the sign-ins' empty Fri 15 replaced by a full Friday, which waits and is then
    published as is. `tour.cjs` gains `upload` to choose a file in a file input.
- **Not yet, for the second part:**
  - The day's story is still judged from its first file: the history keeps each day's first run, so a published
    correction still reads "Almost no sign-ins: 0". What we went with must feed the history.
  - A past day's correction with a later day current is refused by the engine, which never moves a name back. It should
    become what we went with for its day, readers keeping the later day.
  - The recorded story: deliveries in the data, Larkspur's `story.json`, the recorder's decisions, and the day's
    versions.

**Slice 2, second part: the recorded story (2026-11-13):**

- **What we went with feeds the history.** A published correction is how its day is told and learned
  (`learnedMeasures`): the latest run of the day that published, else its first. A later delivery supersedes every
  pause the run it corrects opened (`pausesOf`, `superseded`), but the loads it still reads, which are carried on; a
  superseded pause keeps its decision and no longer keeps its day out of learning, kept back or not.
- **Larkspur's story** (`examples/larkspur/story.json`, `smaltfl-story/1`, core/timeline.ts), named by the data list's

## The questions, decided

The maintainer, 2026-11-13, in a session (docs/OPEN_QUESTIONS.md):

- **Q-180:** a first day near 1 s waits until later, with the work on the engine and smaltts.
- **Q-181:** March is recorded history. The build records the runs, decisions and corrections, and only waiting days are
  the visitor's.
- **Q-182:** the month is a calendar, with a grid of files and steps by day from tablet width.
- **Q-183:** every correction waits for a decision. Every version is kept, like a commit, and you can flip between what
  arrived and what was used. A day can be corrected any number of times.
- **Q-184:** the ontology is effective-dated. A day runs under the rules in force on its date, and its run names their
  hash.
- **Q-185:** the first slice is the two screens and the recorded runs.
- **Q-186:** the posture trend goes on the month. The full dashboard stays its own screen, for the day picked.
- **Q-187:** compare shows a summary and row and cell diffs. Opening any version runs the whole flow and shows what
  would have happened.
- **Q-188:** *for the day* and *as known on*, from the start.
- **Q-189:** a change takes effect from the next day to arrive. Back-dating is a choice, after the form says how many
  past days it would touch.
- **Q-190:** a back-dated change gives each day it touches a version, and one decision restates them, any day
  untickable.
- **Q-191:** what-if runs, marked, kept apart, published only by a decision.
- **Q-192:** the story has a corrected file, a day corrected twice, a late file, and ontology changes forward and
  back-dated.

## Consequences

- **"What happened" is the record**, told day by day.
  - What arrived, what was used and what was published are all hashed and always reachable.
  - A correction adds a version and never rewrites one.
- **The demo opens on a whole month.** A visitor reads first and decides where something waits.
- **Rules become a dated part of the flow.** The same files under the same rules give the same hashes, and a day
  explains itself by the rules it ran under.
- **The demo's results come from the build until the browser re-runs them.** The month shows the build's recorded runs,
  and each day is confirmed only when opened and re-run. That is close to what Q-180 deferred for the first load. Here
  it is history rather than speed, and each day says whether this browser has checked it.
- **The record format grows.** It gains deliveries, the build's entries, as-known-on reads and rules-in-force hashes.
  Each is versioned with test vectors in the slice that adds it.
- **Slice 1 touches every stop set**, since almost all of them pick days.
