## Decision

### 1. Time (ADR 0021)

- **Q-202: a what-if is made the day's in one tap.** The maintainer: "Make it as is but it should be an explicit thing
  that carries over like all the other ways you can do it, so it's not annoying to figure out you like something and
  then you have to go to another screen to confirm it."
  - The what-if's line gains *Make this the day's ›*. Only someone who may decide sees it.
  - The tap is the decision. It asks for a reason, then records the decision and publishes the day's outputs, on the
    same screen.
  - The decision carries the what-if over by the ways a day already gets a version:
    - its files, where they aren't those of the version readers got, become a version of the day (sent again, Q-183);
    - its rules, where they aren't those in force on the day, become a change for that day only, restated (Q-190).
      The next day is back on the rules in force, so only that day is restated, as the what-if showed it. The
      maintainer chose that day only over from that day on, which would also have restated the days after it.
      Slice 1 sets out how a change set says its last day, with test vectors.
  - The one decision decides what that takes, in one entry. Slice 1 sets out how.
- **Q-199: a restatement that changes no day still waits for a sign-off.** A back-dated change can leave every day it
  reaches as it was. That restatement is no longer noted at once: it waits for someone to decide it, as one that
  changes days does (Q-190). Meanwhile the days keep the version readers had.
- **Q-51: a past day's correction leaves readers on the latest day.** A passing run, a correction or a decision about a
  day earlier than the latest one published doesn't move the published names back. That day keeps its own version on
  its screen, and readers' data stays on the latest day. This needs outputs kept by day: ADR 0021 left it unbuilt as
  "a past day's correction while a later day is out".
- **Two gaps ADR 0021 left are closed too:**
  - the offline audit (`src/core/audit.ts`) checks restated runs and restatements;
  - a day restated as not published is no longer learned from by the days after it.
- **Confirmed as built:** Q-196, Q-198, Q-200 and Q-201.

### 2. Columns that change

- **Q-109: a file whose columns don't match pauses the day, in every flow.** A daily file can arrive with a column
  missing, renamed or added. A flow without gates no longer refuses it: the day is held like any other hold, saying what
  changed. Someone who may decide then maps the column, keeps the day back or replaces the file. A gated flow already
  holds such a file under the schema check (ADR 0014 slice 7).
- **Q-146: renamed columns are handled carefully, both kinds.** The maintainer: "Column names need to be addressed in
  ontology. Column name changes need to be handled very carefully. It would be cool to flag it, make a suggestion if it
  seems like it's easy to map the new column name to another old one, or to say I'm confused why this new column. If
  the column is renamed and used for joins, more flags need to go up and the impact needs to be clear and addressed
  with the user."
  - **In an incoming file**, the hold says which column is gone and which is new.
    - Where a new column plainly maps to the old one (its name, its type and its values), the hold suggests the mapping.
      Where it can't tell, it says so.
    - A column a join reads is flagged louder, with what it reaches: the steps and outputs built on that join.
    - A mapping someone confirms is written in the ontology as the file's own, so the next day's file reads it.
  - **The owner's own rename** on the Ontology page first shows where the column is used, joins first, and what it
    reaches. Once applied, the new name is carried through the steps that pass the column on.
- **The design, 2026-11-14** (Q-203 to Q-206, put to the maintainer with a recommended option each; the maintainer said
  to continue, so each is built as recommended, for the maintainers to confirm):
  - **A rename is told by name, type and values.** A mapping is suggested only when the names are close (the same words
    once case, spaces and underscores are set aside, or a letter or two apart), the types are the same, and most of
    today's values were seen in the old column's history, where the file has one. Otherwise the hold says it can't tell
    why the column is new.
  - **An extra column with nothing missing is flagged, not paused.** The day's News says "a new column: X" with an offer
    to add it to the ontology; nothing the flow reads changed.
  - **A join column is confirmed twice.** The hold names each join on it, the steps and outputs built from it, and how
    many of today's values still find a match on the other side; mapping it asks a second confirmation naming those
    outputs.
  - **A mapping counts from the held day on**, as a dated change set: the held day runs again under it and is decided
    as usual, later files read the new name with no hold, and each run's rules hash names it.

### 3. The ontology as the one place for rules

- **Q-176: loose ids are said per check.** Each check that counts objects says whether it matches ids whatever their
  case and spaces: a scope, or the ontology's one row an object. It is no longer said once on the object type.
  Larkspur's checks over the CMDB's ids say it where they need it.
- **Q-118: the gold reconcile key comes from the ontology.** A gold table's `reconcile` takes its key from the
  ontology's `lookup` for the type the table is about. A key written in the gate cell still wins, as with scope (Q-136).
- **Q-119: silver `needs` rules come from the ontology.** A needs rule is written once in the ontology, as a link
  between controls or columns, and applied wherever those datasets are judged. A gate cell can add one or override it.
- **Q-145: drawings say the ontology's label.** A value's label in a drawing is the ontology's, even where it only
  repeats the value ("Not assessed" for not_assessed). Today it is the value as the file writes it.
- **Q-144: a dataset the flow makes has its rules on the Ontology page.** Each made dataset with rules gets a section
  after the files, laid out like a file's. A line under each file it reads names it.
- **Confirmed as built:**
  - Q-134 to Q-137;
  - Q-147: names stay in the flow hash;
  - Q-177: the flow chooses `publish.reach`.

  Q-138 is overtaken by Q-160 to Q-162.

## As built

**Slice 1, first part: a what-if and a restatement decided where they are (2026-11-14):**

- **A change for a day or a few, and a version taken whole** (`ChangeSet.until`, the edit `useVersion`; inforce.ts
  `changesOn`, `resolve`, `versionRules`; `test/inforce.test.ts`):
  - a change set may say its last day: it is in force from its day to then, and never on a run of no day;
  - `useVersion` takes a version's rules whole: the base with its change sets in the order they were recorded, whatever
    their days (none: the rules as shipped). It applies over whatever the change sets before it made of the day's
    rules, said "Took the rules of …", and is passed over where the day already has them;
  - the document checks a last day on or after its day, and a version of change sets recorded before the one that
    takes it;
  - `rules/1` and its vectors are unchanged: a document without either resolves as before. The reach of a change set
    with a last day stops at it, in the page and in the recorder.
- **Make this the day's** (Q-202; the app's `whatIfMakes`, `makePart`, `makeWhatIfTheDays`). It is on the what-if's
  line wherever the what-if isn't the day as readers would have it now, for someone who may publish a day (and the
  owner, where it takes other rules). The tap opens a form on the same screen that says what it does and asks for a
  reason; then it is done in one go:
  - its rules, where other than those in force on the day now: a change set for that day only, taking its version
    (`until`, `useVersion`), said "Took version 1 of the rules (the rules as shipped) for Sat 16 only";
  - other files: a later delivery correcting the run readers got with the what-if's files (`PinOpts.make`,
    `loads.correct`, taken by that run alone), held until a decision (Q-183), decided as is with the reason. The run
    is marked made (`RunRecord.made`, the entry's `made`) and is a version of the day of its own, whatever earlier
    version had the same files (`versionsOfLoad`'s made versions, `madeVersion`), listed as "tls as a what-if had it:
    made the day's";
  - the same files under other rules: the day run again under that change set, and one restatement citing it alone
    decides the day with the reason. Readers get it published where it passes, held where its rules hold it.

  A version is replaced by the next file version in the list, whatever its number (`supersededBy`, Compare's fate,
  the version list). On Larkspur, Thu 21's first TLS file made the day's is a fifth version published as is, and
  Sat 16 under the rules as shipped is a third version restated as published.
- **A restatement that changes no day waits for a sign-off** (Q-199):
  - the page opens the restatement whatever the days came to, and someone who may publish a day signs them off as the
    same, with a reason ("Sign off N days as the same");
  - the day head says such a day waits for the sign-off, and a day the same inside a restatement that changes others is
    noted with it;
  - the recorder signs them off by the story's restatement, never at once.
- **A day restated as not published isn't learned from** (`skipOf`'s `restatedHeld`, hold.ts): a day a restatement made
  held is left out of learning, until a later run of the day publishes, or a later restatement publishes it
  (`test/delivery.test.ts`). On Larkspur, the days after Mon 25 no longer learn from Sat 16 and Sun 17.
- **The offline audit checks restatements** (audit.ts `restatedProblems` and each `restate` entry;
  `test/audit.test.ts`):
  - a restated run is checked as a held run is: its manifest names the run it restates (earlier in the record) and its
    change sets as its entry does, with a restated hold on every output;
  - each restatement is checked:
    - its restated runs are before it, of their days, under its change sets;
    - each day is where `restatedOutcome` puts it: restated or kept where it would change, noted where it wouldn't,
      `passes` as it comes out;
    - its actor may publish a day;
    - it has a reason where it restates or keeps a day;
    - a sign-off with a reason is said as such, and one without as noted at once before ADR 0022;
  - `checksHolds` counts only the checks' holds: a later delivery's or a restated run's own hold made a held run's
    checks look misreported. A restated run is never released, so no release cites a restatement.
- **Found on the way:** smaltnb's notebooks now hold Cypher cells. smaltfl's cell types take `cypher`, and a flow's
  notebook with one is refused by name.
- **Checked:**
  - `npm run check`: 89 files, 1,153 tests;
  - `tools/browser/stops/whatif.json` makes Thu 21's and Sat 16's what-ifs the day's, each form said first;
  - `rules.json` signs off each back-dated edit that changes no day, from the day's head;
  - the browser regression of every stop set of the three demos at phone, tablet, tablet-wide, desktop and wide: 78 of
    78 jobs, 831 stops.

**Slice 1, second part: readers stay on the latest day (Q-51, 2026-11-14):**

- **Outputs kept by day** (`_smaltfl_days(name, day, key, run, prior)` in `src/plugin/store.ts`): the version each day of
  a dataset has, as its last publication left it, and the one it replaced. Versions were never dropped, so a past day's
  stays stored; what was missing was the record of which version is whose day.
  - `publishVersion` keeps a published version as its day's, and moves its name to it unless the name shows a later day
    (`laterShown`), by the plan's periods: `periodsOf` in `src/core/plan.ts` (its period and every watch's, a slot a
    period of its own), `dayKeyOf`, and `periodsAfter`, moved there from `release.ts`.

    later run of its day may be current, or be that day's version.
  - A withdrawal (Q-61) puts the day's own version back to the one the fill replaced, or none. Each name the fill moved

**Slice 2, first part: a file whose columns changed (Q-109, Q-146, Q-203, Q-204, Q-206; 2026-11-15):**

- **A file's header against its source** (`src/core/columns.ts`, `test/columns.test.ts`). smaltdb-io's CSV reader
  picks the declared columns by name only when the header has all of them. Otherwise it refuses a header with another
  number of fields, and reads one with as many by place: a renamed column was read, silently, as the old one. So the
  plugin reads the header itself (`csvHeader`, `csvRecords`, `csvColumn`) before it reads the file.
  - `columnChange(declared, header, { history, today })` says what is gone, what is new, and which new column reads as
    a gone one (`ColumnMap`: by name, type and values, with the share of today's values the history saw).
  - Names are close when they have the same words once case, spaces and underscores are set aside, or are a letter or
    two apart, short names closer (`namesClose`, `wordsOf`, `editDistance`).
  - Types agree by family: text holds codes that read as whole numbers, a number column whole numbers (`familyOf`,
    `inferFamily`, `familiesAgree`).
  - Values count where the watch's history keeps the gone column's (`historyValues`): at least half of today's must have
    been seen (`MAP_SHARE`). Each column is mapped once, the best evidence first.
  - `columnChangeSaid` words it: "result is gone and results is new: results looks like result (its name, type and 100%
    of its values)"; "can't tell why cust_ref is new"; "a new column: notes".
- **The run holds it, in every flow that holds** (Q-109; `src/plugin/runtime.ts`, `test/refused.test.ts`). Before each
  pinned CSV or TSV source with a header is read:

    says what changed (`ManifestNode.columns`, `holdsOf`); the refused file is recorded as pinned, so the day's
    versions find it. A flow without a publish block throws, saying the same;
  - a new column alone is noted on the source's node, and the day is judged and published as any other (Q-204);
  - verify takes a source refused for its columns as coherent in a flow without gates (`changedOnly`);
  - a gated flow's schema check now names the column. The control estate's and Larkspur's Thu Mar 7, whose logging

**Slice 2, second part: a join column confirmed twice, and the owner's rename carried through (Q-205, Q-146;
2026-11-15):**

- **Where a column is used** (`src/core/uses.ts`, `test/uses.test.ts`). `columnUses(doc, source, column, { parse })`
  follows a source's column by its name through the steps:
  - the datasets that carry it (`carried`): a step passes it on when its output has a column of that name taken from an
    input that has it;
  - the joins that match on it (`joins`), each with its other side, a dataset and its column where that side is one
    column of one input;
  - the steps that read it otherwise (`reads`): a filter, a group, a sum, `t0.status AS tls`;
  - the published datasets whose rows depend on it (`outputs`): those that carry it, and everything built from a join
    on it or a read of it. A dataset merely built from one that carries it, using it nowhere, isn't one.

  Typed steps are read from their fields. A SQL step is read from smaltql's parsed SELECT, the parser passed in so the
  core imports none: its FROM items, each CTE and subquery resolved to the inputs it reads (a recursive one ends where
  it reads itself); every join's ON equalities and USING; the columns it selects, a star included. A step matching its
  own rows on the column, as a dedup does, is no join on other data. On the control estate, TLS's app_id is passed on by
  its check and matched by the posture with the inventory's app_id; on Larkspur, the CMDB's id is followed through the
  CTEs that conform it, and the cloud's tags are matched in a subquery. `usesSaid`, `joinsSaid` and `joinImpactSaid`
